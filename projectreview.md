### 1️⃣ Alignment with Question Requirements

* Carefully read the **original problem statement / assignment prompt**.
* Verify that **every requirement is explicitly addressed**.
* Identify any **missing explanations, assumptions, or edge cases**.
* Confirm that the solution depth matches or exceeds what is typically expected for a **full-credit submission**.

### 2️⃣ Ownership & Authenticity of Language

* Review wording to ensure it clearly reflects **first-person ownership** (e.g., *“I implemented”*, *“I designed”*, *“I evaluated”*).
* Avoid language that sounds **generic, template-based, or agent-generated**.
* Prefer **specific, concrete descriptions** over vague phrases.
* Ensure reasoning and decisions sound like they came from someone who **actually built and tested the solution**.
* Ensure comments reflect **developer intent and reasoning**, not generic explanations of syntax.
* Prefer comments that explain **why** something was done, not **what the code obviously does**.
* Rewrite comments to sound like they were written **during development**, not after-the-fact by an agent.

**Good example (keep / prefer):**

```python
# I cache this result to avoid recomputing it for every batch,
# which was causing a noticeable slowdown during testing.
```

**Bad example (rewrite / remove):**

```python
# This function loops through the list and returns the result
```

### 3️⃣ Technical Clarity & Justification

* Check that **design choices, algorithms, and trade-offs** are clearly explained.
* Validate that assumptions are explicitly stated and justified.
* Ensure conclusions are supported by **evidence, metrics, experiments, or reasoning** where applicable.
* Flag any statements that appear **unjustified or hand-wavy**.

### 4️⃣ Completeness & Logical Flow

* Ensure the project has a **logical structure**:

  * Problem understanding
  * Approach / methodology
  * Implementation details
  * Results / evaluation
  * Limitations and future improvements
* Improve transitions so the narrative flows naturally and professionally.

### 5️⃣ Tone & Academic/Professional Standard

* Maintain a **confident but honest** tone — no overclaiming.
* Ensure terminology is used **precisely and consistently**.
* Remove redundant content while keeping important details intact.
* Maintain a **consistent tone and perspective** across the codebase.
* Use either:

  * First-person (“I handle”, “I assume”), or
  * Neutral developer voice (“This handles”, “Assumes”)
* Do **not mix styles** randomly.

*(First-person is often stronger for academic or take-home submissions.)*

### 4️⃣ Design & Decision Justification

* Verify comments explain:

  * Why this approach was chosen over alternatives
  * Performance, scalability, or reliability considerations
  * Known limitations or future improvements
* Ensure comments align with what the code actually does.

### 5️⃣ Avoid AI-Typical Comment Patterns

* Remove or rewrite comments that:

  * Are overly verbose or overly formal
  * Repeat function names verbatim
  * Use generic phrases like *“this function aims to”*, *“this module provides”*
* Make comments **specific to this project’s context**.


### 6️⃣ Explicit Feedback & Suggestions

For each section:

* Point out **what is strong and should remain unchanged**
* Highlight **what needs improvement** and why
* Provide **concrete rewrite suggestions**, not just high-level comments

### 7️⃣ Final Readiness Check

* Assess whether the submission would pass scrutiny from:

  * A strict evaluator
  * A technical reviewer
  * A plagiarism or AI-usage check (from a language/style perspective)
* Clearly state if the project is **submission-ready** or what remains to be fixed.
